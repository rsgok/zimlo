# Zimlo 产品优化评估 · 2026-09-05

Zimlo 最值得做深的价值是：用户离开电脑后，仍能及时发现需要自己的事情，可靠地处理，并确认 Agent 已经继续工作。所有优化围绕减少等待、减少理解成本、减少重复操作、增加可验证的信任展开。

## 评估范围与证据等级

- 本次检查：当前 checkout `6a7d20e`、已安装 macOS App 的 Feed / Tasks / 设置 / 新任务界面、本机进程与端口、只读数据库聚合、Web / iOS / macOS / Rust / Cloud 源码、官网源码、CI 工作流。
- 安装的 macOS App 为 `0.3.0 (1)`；运行中的 Mac Rust Runtime 来自 `0.3.0-1-arm64-bb063a181dbc`。当前源码与安装包不能视为完全同一版本；下文分别标明现场现象与当前代码证据。
- 本次运行 `pnpm test`：82 个测试文件、451 个测试通过；`pnpm architecture:check`：333 个源文件检查通过。
- 未进行 iPhone 真机交互、APNs 真机投递、弱网故障注入、完整发布构建、用户访谈或线上转化统计。本报告不将这些体验宣称为已验证。
- **实测**代表本次直接观察；**代码风险**代表可定位的实现与推导，尚未注入故障复现；**产品假设**代表需要试用数据验证的方向。
- 下文的验收数值是建议目标，除明确标注的现场数据与历史报告外，不是现状成绩。

## 先保留已有优势

1. iPhone 优先，Feed 只承载值得阅读的结果、行动和失败；用户原始指令留在任务详情。
2. 已有设备级加密、权限、审批审计、可撤销操作、弱网 outbox、草稿、通知路由和多设备归属。
3. Rust 已成为默认 Runtime，Node 保留为迁移参考；不需要再发起一轮语言替换。
4. 已有共享协议、生成常量与跨语言测试向量；优化应补齐行为一致性。
5. 核心验收继续采用既定方向：3 秒判断需要关注什么、10 秒完成常规处理、20 秒布置常见新任务。高风险审批保留充分阅读与确认。

### O01：先解决“连得上，但连错了”

本次现场观察：

- Mac App 显示“已连接”；Tasks 为 0，Feed 显示 `All Caught Up`。
- `127.0.0.1:4747/api/local/snapshot` 返回的 host 为 `Linux Server / linux`，所有项目、session、帖子与任务数组为空，sequence 为 0。
- Mac 本地服务描述符指向 PID 7361、4747 端口；该 PID 的确是本机安装的 Rust Runtime。
- `lsof` 同时显示 Zimlo 监听 `*:4747`，OrbStack 监听 `127.0.0.1:4747`。
- 只读本机数据库得到 151 个 session、6 个项目、9 条 Feed、108 条 task；数据库 host 身份与 HTTP 返回的 Linux host 不同。

这证明界面使用的 loopback 服务与本机数据库不是同一设备的数据源。OrbStack 的具体转发配置没有修改或进一步验证；端口竞争 / 转发是与现象高度吻合的机制，不应把空列表归因为任务丢失。

当前代码在 `apps/macos/Sources/ZimloMac/ServiceController.swift:355` 只检查 `/healthz` 的协议兼容性；`ServiceContracts.swift` 的 `HealthResponse` 只解码 `protocolVersion`。另一个合法 Zimlo 实例也会通过检查。

建议：

- 服务描述符与健康握手提供稳定 hostId、启动实例标识、build revision；本地 App 复用服务时验证身份和本地进程归属。
- 身份校验不能只信任 HTTP 自报字段；使用受当前用户权限保护的 Unix socket / 本机凭证建立预期身份，HTTP 探测再与其关联。
- 对错误实例展示明确的设备名称与恢复路径，阻止向错误实例执行本机管理操作。
- 顶栏可简洁显示运行设备；端口、进程、版本等放进诊断详情。手动添加的 Linux host 仍是合法远程来源，与本地服务复用区分。

验收：Mac + Linux 容器共用常见端口时，要么连接预期实例，要么明确报告冲突；绝不显示错误设备的“本机已连接”。覆盖旧 descriptor、PID 复用、App/Runtime 不同版本、服务重启、身份变化。

### O02：三端采用相同的 Feed 行为规则

`apps/macos/Sources/ZimloMac/NativeFeedView.swift:7` 从 `snapshot.posts` 建列表，并按待审批、未读、时间重新排序。`NativeFeedCard` 又在出现后标记已读。因此，已读更新存在改变列表顺序的代码路径；只有 action、没有 post 的任务也不会被这份 Feed 列表独立收录。

Web 的 `FeedView.tsx` 已使用固定序列；iOS 的 `AppModel.swift` 会加入独立 action。现有实现证明所需规则已经存在，不必重新设计。

建议：

- 三端共享条目类别与排序输入：独立审批、明确失败、结果、可审阅进展；帖子不是审批出现的前提。
- 一次阅读会话内固定队列和当前卡片锚点；已读、审批完成、后台刷新改变卡片内容，不移动正在看的卡。
- 新的紧急操作提供明确但克制的入口，用户主动进入；普通结果沿用现有“有新内容”规则。
- 同一任务的多个待处理 action 都可被找到，避免仅展示 `first` pending action。
- `All Caught Up` 只用于已成功同步且没有待处理内容的状态。

验收：一个从未发帖的任务产生审批仍能进入 Feed；连续阅读 20 张卡不因已读而换位；4 个同时审批分别指向正确任务；全部已读与尚未接入拥有不同空状态。

### O03：Mac 发送也要具备可恢复的确认链路

`NativeAppStore.swift:202` 直接发送 HTTP；`createTask / followUp` 在每次调用时新建 UUID（244、254 行）。`NativeComposerView.swift` 保存文字草稿，但附件是视图内的 `@State`，发送成功后才关闭输入面板。

代码风险：服务端已接受而响应丢失时，用户再次提交会得到新的幂等键，可能形成第二个任务或第二次回复。本次没有向真实任务注入故障，未声称已发生重复执行。

建议将 Web/iOS 的可靠发送规则补齐到 Mac：

1. 一次用户发送意图先生成稳定 commandId / idempotencyKey，连同正文、目标与附件清单持久化。
2. 持久化成功即可展示“已保存，等待发送”，再异步发送。
3. 回执未知时保留同一个键，查询服务端状态或幂等重发；重新编辑才创建新意图。
4. 界面区分“已保存 / 设备已收到 / Agent 已开始 / 需要处理”，不要把网络提交等同于开始执行。
5. 文字和附件恢复范围一致；失败后可重试、重新编辑或撤回适用的 queued 命令。

验收：覆盖发送前退出、发送后回执丢失、重复点击、切换任务、Runtime 重启、附件未完成；同一意图最多执行一次。回执未知时不自动宣称失败或成功。

### O04：首次成功操作才算完成接入

现场的新任务面板显示“暂无可信项目”，发送禁用，但面板没有直接建立可用项目的下一步。当前现场还受到 O01 错误数据源影响；空工作区本身也是需要覆盖的合法首次安装状态。

建议把 onboarding 的完成条件定义为：正确后台 → 检测到可用 Agent → 用户选择一个项目 → 手机配对 → 看到一条真实结果或完成一次无风险操作。

- 先推荐检测到的可用 Agent，其他 provider 的接入状态收进详情；避免用户以为四种 GUI/CLI 都必须配置。
- “暂无可信项目”附带“选择项目”或返回本机建立授权的直接入口，不自动扩大权限。
- 空 Feed 按状态给出一个主行动：连接设备、接入 Agent、选择项目、查看进行中任务，或明确“暂时没有需要你处理的事”。
- 引导阶段可提供有明确演示标识的样例卡；完成标准仍是一个真实闭环。
- 一次失败后保留已完成步骤和错误处的上下文。

建议目标：从两端已安装且 provider 已登录开始，首次成功同步 p90 ≤ 2 分钟；常见新任务创建在 20 秒内完成。先用 5–8 位目标用户观察逐步耗时，再调整目标。

### O05：性能预算围绕真实使用建立

仓库 `docs/RUNTIME_PERFORMANCE.md` 的 9 月 1 日报告显示：空库、关闭 Cloud 的实验中，Rust 冷启动 p50 约 19.42ms、RSS 约 15.2MB。这是已完成的优化，但不能代表手机的打开速度或真实数据量下的表现。本次 Mac Runtime 单次 `ps` RSS 约 30MB，也不是稳定态压测。

当前可优化路径：

- `NativeAppStore.swift:168` 每 2 秒获取全量 Snapshot；sequence 相同时也可能重新赋值并触发派生状态计算。
- Rust `websocket.rs` 每个连接以 250ms 轮询设备状态 / 数据版本，变更时发送全量 Snapshot。
- `zimlo-store/src/snapshot.rs:400` 每次生成首次输入映射都读取全部 `user_instruction` 事件；task/session 查询还需要大样本预算。
- Feed Snapshot 上限 200 条，material 上限 500 条；需要把当前窗口与历史分页分开设计，否则“有上限”和“历史可找回”难以同时兑现。

优化顺序：

1. 测量打开缓存、首次新鲜数据、命令接收、Agent 开始、媒体首屏与翻页；按网络和 host 分桶，避免只看平均值。
2. Mac 按可见性 / 活跃程度调整刷新，未变化的读模型避免重新发布；进程发现改为事件驱动优先、低频巡检兜底。
3. 建立按领域的 revision / 变更通知，在保持现有撤销设备检查及时性的前提下减少重复轮询。
4. 初次全量 + 后续增量 + 游标补偿；断序或兼容失败回退全量，不牺牲恢复正确性。
5. 任务首条输入持久化或维护可索引的读模型；先用查询计划和实际数据验证收益。
6. 媒体先缩略图后原件，附近卡片预取，离屏暂停视频，限制缓存与并发解密；保持加密与内容校验。

| 指标 | 建议首轮目标 | 测量条件 |
|---|---|---|
| 本地发送反馈 | p95 ≤ 100ms | 本地持久化完成，不含网络 |
| 手机重新打开后的缓存首屏 | p95 ≤ 500ms | 普通目标 iPhone，已有缓存 |
| 正常网络下新鲜状态到达 | p95 ≤ 2s | Host 在线，分别测 LAN 与 Cloud |
| 常规审批 / 回复闭环 | 10 秒内 | 包含理解、操作和回执；高风险单独评估 |
| 大数据交互 | 1k session / 10k post / 100k event 下通过交互预算 | 1 / 3 / 5 host、冷/热缓存，测 p50/p95/p99 |
| 空闲资源 | 先建立基线，再设相对回归门禁 | 8 小时待机 CPU、唤醒次数、能耗与网络字节 |

官网与 Web 的基础门槛可采用 p75 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1；这些来自 [Google Web Vitals 官方说明](https://web.dev/articles/vitals)，不是本次测得的成绩。

### O06：测试从规则覆盖延伸到真实安装包与三端流程

当前 451 项 TS 测试通过、架构门禁通过，仓库也已有 Rust 与跨语言 smoke。缺口是：`.github/workflows/ci.yml` 调用 `pnpm check`，但该命令不含 `macos:test`、站点检查或 iOS XCTest；`release-ios.yml` 直接走 archive / upload，文件内未运行测试。存在测试文件与每次发布实际执行测试是两件不同的事。

建议：

- PR 门禁加入相关 Swift 测试和最小 iOS 构建 / XCTest；站点按路径触发检查。
- 发布只接收已经通过对应检查的同一 commit，保留 commit、App build、Runtime build、协议与能力清单的对应关系。
- 每次发布执行少量高价值端到端场景：首次接入、错 host、无 post 审批、回执丢失、重启恢复、权限撤销、旧版本升级。
- 网络与 provider 使用可控假服务做故障注入；定期对真实 provider 版本和手机 APNs 做人工 / 真机验收。
- 发布后做下载工件安装冒烟，分批更新，保留可回滚工件。数据库迁移有兼容检查与恢复演练。
- `0.3.0` App / `0.2.1` Runtime 产品常量 / protocol 5 可以是有意分层，但诊断里必须清楚命名，避免一个“版本号”承担三种含义。

### O07：官网把承诺接到可执行的下一步

`landing-page/app/page.tsx` 围绕 iPhone Beta 宣传；直接下载分支 `BetaDownload.tsx:107` 只输出 Apple silicon / Intel Mac 下载。开启 waitlist 时还有另一条入口，因此不能据此断言线上完全没有 Beta 获取路径；本次未核实部署开关与 TestFlight 当前可用性。

建议：

- 首屏主张突出“离开电脑，也能批准、回复并看见 Agent 继续工作”，弱化 TikTok / X 这些对界面形式的解释。
- 用 30 秒真实录屏展示：离开电脑 → 收到审批 → 看上下文 → 批准 → 任务继续 → 打开成果。
- Mac / iPhone 安装入口并列，按当前访问设备推荐下一步；TestFlight 未开放就明确说明获取方式。
- 同步 Linux 已支持这一事实，区分 Mac 的零终端路径和 Linux 的 SSH 安装路径。
- 只有内容明确可公开的素材才用于官网，成果分享默认脱敏并让用户主动选择。

## 继续做深的产品方向

### 注意力与任务设计

- 首页回答三个问题：现在需要我做什么、为什么需要我、做完会发生什么。常规状态与历史放在任务详情，维持一屏一卡。
- 每个任务的“下一步”应区分用户输入、Agent 执行、外部依赖、已结束；显示简短原因、来源设备和更新时间。
- 当 Agent 不能被安全继续时，说明约束并给出明确可行入口，不让用户反复点击无法完成的操作。
- 有多项审批时可连续处理并保持上下文；默认不做宽泛批量批准。
- 常用指令可保存为个人模板，例如检查改动、解释失败、继续任务；先从用户真实重复输入中选 3–5 个。

### 视觉与可访问性

- 统一中文术语与状态文案，避免一个中文界面同时出现 `All Caught Up`、Runtime、Bridge 等不同层次用语。技术诊断保留准确原名。
- Mac 当前部分辅助文字是 9.5–11pt 固定字号；提高重要提示的可读性，用语义字体表达层级，减少靠灰度和小字隐藏关键信息。
- 手机正文、操作按钮、长标题、横屏、大字号、VoiceOver、减少动态效果逐项走真实流程。源码已有部分支持，应验证完整体验，而不是当作从零新增。
- 手势保留按钮或辅助功能等价入口；审批目的、目标、设备、风险与确认必须完整可读。
- 用“理解和完成操作的时间”验证设计变化；留白、动效和卡片主题服务于阅读，不单独作为成果指标。

### 成果与长期价值

- 在任务和 Agent 内建立成果检索：按项目、时间、文件类型找到真实产物与最新结论；不急于增加一个一级导航。
- 文件预览显示生成来源、版本、大小和离线可用状态；已失效或设备离线时提供可理解的状态。
- 对需回电脑继续的成果，提供准确任务路由与打开位置；避免只得到一段“文件已生成”的文字。
- 历史检索要补齐游标 API 与保留策略，再承诺长期成果库；不能只扩大当前 Snapshot 上限。

### 安全、隐私与恢复

已有 E2EE、Keychain、文件保护、审批权限与脱敏基础。下一阶段重点验证信任边界与恢复行为：

- 本机管理面核对 host、进程归属、调用者与来源；测试浏览器 Origin / Host 变化、DNS rebinding、容器转发。这是测试清单，不是本次已验证的可利用漏洞。
- 设备撤销、审批过期、权限降低、多 host 同 session 标识时，队列重放必须重新检查授权，失败给出准确原因。
- 备份、导出、升级恢复与缓存清理有可理解的入口；诊断包先脱敏并可预览。
- 通知优先准确和及时：审批 / 失败直达正确任务；睡眠唤醒、手机切网和丢路由需要恢复验证。
- 保持“任务正文不存入云端”的现有边界。产品度量默认本地聚合；任何远程上传方案都要重新核对隐私声明与用户选择。

### 架构与维护成本

- iOS `AppModel.swift` 1298 行、`SecondaryViews.swift` 1332 行，Web `useBridge.ts` 791 行；行数只是定位职责集中的信号，不是重构的充分理由。
- 首先提取已经出现行为分叉的 Outbox、FeedSequence、HostRouting、SnapshotRepository，再按真实变更拆分 UI。

### 度量、用户群与商业验证

建议首先服务“经常离开电脑、同时运行多项 Codex / Claude 工作”的个人开发者。此用户群与当前产品能力匹配，是待验证的定位假设。

建议主指标：**每周在手机上成功处理、得到后续确认的有效任务数**。辅助指标：

- 激活：正确连接 → 发现任务 → 手机首次处理 → 收到确认的逐步完成率与耗时。
- 可靠性：未知回执比例、重复执行事件、超过时限仍未恢复的命令、错 host 事件。
- 注意力质量：有用卡片反馈、无效提醒比例、从提醒到处理的耗时。
- 留存：首周和第四周仍完成有效操作的用户比例；先建立 cohort 基线，不虚构现有数值。
- 成本：每活跃 host 的连接时长、消息数、转发字节、媒体暂存与推送量，算出真实单位成本。

本次在主要应用源码中没有找到常见产品分析 / 性能埋点 SDK；这不证明完全没有运营数据。先增加本地可查看的聚合诊断和小规模试用观察，不默认上传标题、正文、路径或用户标识。

先用 5–8 位目标用户做引导观察，再开展约两周的日常试用。收费方向可验证“多设备管理、成果整理、团队协作”等持续价值；基本发送可靠性与安全不应被拆成付费补丁。具体价格等真实使用频次、成本与支付意愿有证据后再确定。
